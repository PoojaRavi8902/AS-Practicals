9.1.1 — Top‑down design & modular programming
Expand

Top‑down design (also called stepwise refinement) begins with a high‑level description of the program and repeatedly breaks it down into smaller modules until each module is simple enough to implement. Modular programming organises code into independent units (procedures, functions, modules) with clear responsibilities. This approach reduces complexity, encourages reuse, and makes testing manageable.

My tip: When planning, draw a module hierarchy chart — it makes dependencies and data flow obvious to students.
Example: For a simple banking system start with: ProcessTransaction(); within it: AuthenticateUser(), CheckBalance(), UpdateAccount(), PrintReceipt().
Exercise: Decompose an online exam platform into at least six modules and state what each should do.
9.1.2 — Procedures and Functions
Expand

Procedures (sometimes called subroutines) perform actions but do not necessarily return a value. Functions compute and return a value. Both are used to encapsulate behaviour: a procedure might print a report, while a function might calculate and return a total.

// Pseudocode examples
PROCEDURE PrintReceipt(accountID)
  // fetch and print details
ENDPROCEDURE

FUNCTION CalculateInterest(balance, rate)
  interest ← balance * rate / 100
  RETURN interest
ENDFUNCTION
My tip: Teach students to ask: "Does this unit need to return data?" — if yes, make it a function; if no, a procedure is fine.
Exercise: Convert the earlier module UpdateAccount() into a procedure and CalculateInterest() into a function; write pseudocode for both.
9.1.3 — Parameters and Arguments (Pass by value / reference)
Expand

Parameters are named variables in the procedure/function definition; arguments are the actual values passed during a call. There are two conceptual passing methods: by value (a copy is passed; changes do not affect the caller) and by reference (a reference to the original variable is passed; changes affect the caller). Many exam pseudocode frameworks assume pass-by-value unless specified otherwise — but students should understand both concepts.

// By value (conceptual)
PROCEDURE Increase(x)
  x ← x + 1
ENDPROCEDURE
// Calling with n: Increase(n)  -> n unchanged if pass-by-value

// By reference (conceptual)
PROCEDURE IncreaseRef(&x)
  x ← x + 1
ENDPROCEDURE
// Calling with n: IncreaseRef(n) -> n is incremented if pass-by-reference
My tip: Use simple number examples to show the difference. Avoid language‑specific jargon; emphasise the effect on the original variable.
Exercise: Write pseudocode showing a function that swaps two variables using pass-by-reference. Then explain why pass-by-value alone cannot swap them.
9.1.4 — Variable scope and lifetime
Expand

Scope defines where a variable is visible. Local variables exist only within a procedure/function; global variables are accessible from any module. Lifetime refers to how long a variable exists in memory — local variables typically exist only while the procedure runs, whereas global variables persist for the program's duration. Scope and lifetime affect correctness and maintainability: excessive use of globals can create hidden dependencies and bugs.

9.1.5 — Advantages of structured programming
Expand

Structured programming promotes readability, maintainability, and easier debugging. It reduces complexity through modularisation and clarifies data flow and control flow. For exam answers, clearly describe modular decomposition and justify choices — examiners reward systematic design and clear identifier tables.

Example (exam tip): When asked to design a system, include a module list, brief pseudocode for each module, and an identifier table.

9.2 — Programming Constructs (detailed examples)

9.2.1 — Sequence
Expand

Sequence is the default execution order: statements run one after another. Most algorithms are a mix of sequence with selection and iteration. Emphasise clear assignments and initialization.

// Pseudocode: Calculate sum of first N natural numbers
INPUT N
sum ← 0
FOR i ← 1 TO N
  sum ← sum + i
NEXT i
OUTPUT sum
Exercise: Rewrite the above using a WHILE loop instead of FOR.
9.2.2 — Selection (IF / CASE)
Expand

Selection lets the program choose between alternatives. Use IF…ELSE for simple branching and CASE (or SELECT) for multiple alternatives. Teach students to handle all possible branches and provide default cases.

IF score >= 90 THEN
  grade ← 'A'
ELSE IF score >= 75 THEN
  grade ← 'B'
ELSE
  grade ← 'C'
ENDIF
My tip: In exams, always state what happens for boundary values (e.g., score = 75) — this prevents lost marks.
Exercise: Convert the IF ladder above into a CASE/SELECT structure (pseudocode style).
9.2.3 — Iteration (FOR, WHILE, REPEAT UNTIL)
Expand

Iterations repeat steps. FOR loops are used when the number of iterations is known; WHILE and REPEAT UNTIL are used when the continuation condition depends on runtime data. Teach students to avoid infinite loops by ensuring the loop variable changes correctly.

// WHILE example: Read numbers until a negative number entered
sum ← 0
INPUT x
WHILE x >= 0 DO
  sum ← sum + x
  INPUT x
ENDWHILE
OUTPUT sum
Exercise: Explain an off‑by‑one error with a simple FOR loop example and show how to fix it.

9.3 — Using Arrays and Records in Algorithms

Arrays · Records · Traversal · Searching · Updating
Collapsed
9.3.1 — Single‑dimensional arrays
Expand

An array is an indexed collection of elements of the same type. Single‑dimensional arrays are used for lists. Operations include traversal, insertion, deletion (logical or physical), and searching.

// Pseudocode: Find maximum in an array
max ← array[0]
FOR i ← 1 TO Length(array)-1
  IF array[i] > max THEN
    max ← array[i]
  ENDIF
NEXT i
OUTPUT max
Exercise: Write pseudocode to compute the average of numbers stored in array Readings with N elements.
9.3.2 — Multi‑dimensional arrays (overview)
Expand

Multi‑dimensional arrays (e.g., 2D arrays) model tables or matrices. Traversal uses nested loops. For AS level, treat them conceptually and provide simple examples like a 2D grid of scores.

// Example: Sum all elements in a 2D matrix
sum ← 0
FOR r ← 0 TO rows-1
  FOR c ← 0 TO cols-1
    sum ← sum + matrix[r][c]
  NEXT c
NEXT r
OUTPUT sum
9.3.3 — Records (structured data)
Expand

Records (also called structs) group related fields of different types under a single identifier. They are useful for representing entities such as Students with fields (ID, Name, Marks).

// Example record
RECORD Student
  ID: Integer
  Name: String
  Mark: Integer
ENDRECORD

students[0].Name ← "Aisha"
Exercise: Show how to search for a student by ID in an array of Student records.
9.3.4 — Traversal, searching, and updating
Expand

Traversal visits each element; searching looks for an element (linear search or binary search for sorted arrays); updating modifies data in place. For AS, focus on linear search and simple traversal algorithms.

// Linear search
FOUND ← FALSE
FOR i ← 0 TO Length(array)-1
  IF array[i] = KEY THEN
    FOUND ← TRUE
    BREAK
  ENDIF
NEXT i
My tip: Teach students to check sorted/unsorted status — choose binary search only if array is sorted; otherwise use linear search.

9.4 — Program Development and Testing

Development stages · Testing strategies · Test data
Collapsed
9.4.1 — Stages of program development
Expand

Typical stages: Requirements → Design → Implementation → Testing → Deployment → Maintenance. Emphasise documentation at each stage and maintaining identifier tables and module descriptions for exam answers.

Example: For an online shop, specify input (productID, quantity), process (check stock, calculate price), and output (order confirmation).
9.4.2 — Testing strategies (black‑box, white‑box, boundary)
Expand

Black‑box testing focuses on input/output behaviour without reference to internal code; white‑box testing examines internal paths and branches; boundary testing checks edge values (e.g., 0, 1, max). Use a mix of all for robust testing.

Exercise: Provide test cases for a function that calculates grade based on score: 0–100. Include valid, invalid, and boundary cases.
9.4.3 — Producing and using test data sets
Expand

Good test sets include normal cases, boundary cases, and exceptional cases. Document expected output for each test and use trace tables to show step‑by‑step variable changes for failing tests.

Example test set: For input age: [-1 (invalid), 0 (boundary), 17 (normal), 120 (boundary), 121 (invalid)].
9.4.4 — Debugging and code maintenance
Expand

Debugging is an iterative process of locating defects and correcting them. Good maintenance practices include comments, modularity, and versioning. Show students how to record a bug log: description, steps to reproduce, expected vs actual, fix applied.

My tip: Encourage students to write clear commit messages and short comments above complex logic blocks.

9.5 — Good Programming Practice

Readability · Naming · Documentation · Reusability
Collapsed
9.5.1 — Readability, indentation, comments
Expand

Readable code uses consistent indentation, meaningful names and concise comments. For pseudocode in exams, use consistent indentation to show structure clearly — examiners expect neat, well‑organised answers.

Example: Show the difference between unindented and properly indented pseudocode for nested IFs.
9.5.2 — Naming conventions and documentation
Expand

Use descriptive names: TotalMarks, StudentID. Document functions with a short header: purpose, parameters, return value, side effects. Maintain identifier tables and module descriptions for full marks in design questions.

Exercise: Provide a documentation header for a function SortList(List) describing its behaviour, parameters and return value.
9.5.3 — Reusability and maintainability
Expand

Write small, well‑tested modules with clear interfaces so they can be reused in future programs. Avoid tight coupling between modules; prefer well‑defined parameter lists and return values. Keep code DRY (Don't Repeat Yourself).

My tip: Encourage writing small helper functions even for classroom exercises — students will thank you during tests.
