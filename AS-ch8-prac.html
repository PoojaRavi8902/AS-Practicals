8.1.1 Abstraction — the need, benefits & producing abstract models
Expand

Definition: Abstraction removes unneeded details and keeps only essential features of a problem.

Teacher notes:

When teaching: use several real-world examples — e.g., mapping a car to attributes vs describing the engine internals. Ask students to practise by abstracting everyday objects (phone, classroom, library).

Clear example

Problem: Create an attendance system for a school. Abstract model:

Student: { ID, Name, Class, Status }
Class: { Name, RoomNumber, Teacher }
AttendanceRecord: { StudentID, Date, Present }

  • Patient: {PatientID, Name, DOB}

  • Appointment: {AppID, PatientID, Date}
  • Ward: {WardID, Name, Capacity}
  • Prescription: {PrescID, PatientID, Medication}

Teaching tip

Ask students to compare their models — there is not a single correct abstraction; the aim is to capture essentials for the system's purpose.

8.1.2 Decomposition — breaking down a problem into sub-problems & modules
Expand

Definition: Decomposition divides a complex task into smaller, manageable parts, each of which can be implemented and tested separately.

Worked example (Library system)

  1. Search catalogue
  2. Borrow / Issue book
  3. Return book & update availability
  4. Calculate fines
  5. Manage member records

Module mapping (procedures/functions):

PROCEDURE SearchCatalogue(query)
PROCEDURE IssueBook(memberID, bookID)
PROCEDURE ReturnBook(bookID)
FUNCTION CalculateFine(daysLate)
PROCEDURE UpdateMember(memberID)

Exercise 2 (medium)

Task: Decompose an online quiz platform into at least 6 modules (name & purpose). Then suggest which could be functions vs procedures.
  1. UserAuth(): handles login/registration (procedure)
  2. LoadQuiz(quizID): fetches questions (function)
  3. StartTimer(duration): controls timing (procedure)
  4. SubmitAnswers(userID, answers): records responses (procedure)
  5. GradeQuiz(answers): returns score (function)
  6. ShowResults(userID): displays feedback (procedure)

Teacher: emphasise how decomposition simplifies testing — unit test each module.

8.1.4 Algorithmic thinking — plan step-by-step logic before coding
Expand

Teach students to write the steps in plain language or structured English before converting to pseudocode.

Worked example — Average of N numbers (structured English → pseudocode)

Structured English:
1. Read the number of items N
2. Set Total to 0
3. Repeat N times: Read a number and add to Total
4. Calculate Average = Total / N
5. Output Average

Pseudocode:
INPUT N
Total ← 0
FOR I ← 1 TO N
  INPUT Value
  Total ← Total + Value
NEXT I
Average ← Total / N
OUTPUT Average

Exercise 4 (exam-style)

Task: Write structured English and then pseudocode for: "Given a list of student marks, count how many students scored >= 75%". 
Structured English:
1. Read number of students N
2. Set Count to 0
3. Repeat N times: Read Mark. If Mark >= 75 then Count ← Count + 1
4. Output Count

Pseudocode:
INPUT N
Count ← 0
FOR I ← 1 TO N
  INPUT Mark
  IF Mark >= 75 THEN
    Count ← Count + 1
  ENDIF
NEXT I
OUTPUT Count

8.2.1 — Definition of an algorithm
Expand

An algorithm is a finite, unambiguous sequence of steps to solve a problem. It must terminate and be correct for all valid inputs.

Quick checklist for a valid algorithm

  • Clear start and end
  • No ambiguous instructions
  • Terminates in finite steps
  • Handles edge cases

Exercise 5 (short)

Task: Which of the following is NOT an algorithm? Explain briefly.
  1. A recipe for baking a cake
  2. A list of all prime numbers (without rules)
  3. A step-by-step assembly guide for furniture
(b) A list of primes without a generating rule is not an algorithm because it does not describe a procedure to produce primes; it's only data.
8.2.2 — Methods: Structured English, Pseudocode, Flowchart
Expand

Use the representation that best communicates the algorithm. For exams, pseudocode and flowcharts are common.

Common pseudocode keywords & examples

INPUT, OUTPUT, IF, THEN, ELSE, ENDIF, FOR, WHILE, REPEAT, UNTIL, RETURN, CALL

Example:
INPUT A, B
IF A > B THEN
  OUTPUT "A is larger"
ELSE
  OUTPUT "B is larger"
ENDIF

Flowchart mini-diagram (textual)

Start -> [Input A,B] -> <(Decision A>B?)> -> yes -> [Output A is larger] -> End
                                                   -> no  -> [Output B is larger] -> End

Exercise 6 (medium)

Task: Convert the following pseudocode to structured English and to a simple flowchart description: 
INPUT N
Sum ← 0
FOR I ← 1 TO N
  Sum ← Sum + I
NEXT I
OUTPUT Sum

Structured English: Read N. Set Sum to 0. For I from 1 to N add I to Sum. Display Sum.

Flowchart description: Start → Input N → Set Sum=0 → Loop (I=1..N: Sum=Sum+I) → Output Sum → End.

FOR loop:
INPUT N
Fact ← 1
FOR I ← 1 TO N
  Fact ← Fact * I
NEXT I

WHILE loop:
INPUT N
Fact ← 1
I ← 1
WHILE I <= N DO
  Fact ← Fact * I
  I ← I + 1
ENDWHILE
OUTPUT Fact

Exercise 10 (short)

Task: What is the result of the condition: IF NOT (A OR B) when A=false and B=true? Explain.
A OR B = true, NOT(true) = false. So the condition is false.

Expand

Use clear keywords, assignment arrow, meaningful names, and indentation. Avoid language-specific syntax.

Expand

8.4.2 — Identifying errors & debugging
Expand

Common errors and how to find them using trace tables and boundary tests.

Example — Off-by-one error

Pseudocode that loops from 1 to N but uses array indexing starting at 0 can skip or cause errors. Teach students to check loop bounds.

Exercise 16 (debugging)

Task: The following pseudocode is intended to reverse a list but gives incorrect results. Spot the error: 
FOR I ← 1 TO Length(list)
  Reversed[I] ← list[Length(list) - I]
NEXT I
Indexing is inconsistent. Correct (0-based): FOR I ← 0 TO Length(list)-1 Reversed[I] ← list[Length(list)-1 - I] NEXT I

8.5 — Efficiency & Complexity (AS-level overview)

Qualitative efficiency · Choosing algorithms
Collapsed
8.5.1 — Basic measure of efficiency
Expand

Explain time & space informally. Use examples like linear vs binary search (qualitative explanation only).

Example — Linear vs Binary search

Linear search checks each item until found (O(n) conceptually). Binary search splits sorted list each time (faster for large sorted lists).

Exercise 18 (conceptual)

Task: For a sorted list of 1,000 names, which search is preferable and why? (short answer)
Binary search — it halves the search space each step, so far fewer comparisons than checking every name.
8.5.2 — Choosing appropriate algorithm
Expand

Balance simplicity, correctness and performance. For AS-level prefer clear, testable algorithms.

Exercise 19 (exam-style)

Task: Suggest an approach to sort a small list (<=20 items) for classroom use and justify your choice.
Use Bubble sort or Insertion sort — simple to understand and easy to trace in class despite not being optimal for large datasets.
